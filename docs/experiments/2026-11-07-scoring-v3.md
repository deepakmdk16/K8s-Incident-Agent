# Pre-registration — scoring v3: score the fix, not the sentence (STATUS 3.1)

Written BEFORE `evals/scoring_v3.py` was run over any bundle. The gold tree
(`evals/gold-v3/`) and the normalizer were authored from the scenarios and
are frozen at the commit that carries this section; the Result section below
is appended afterwards and reports whatever the run returned.

## What is being measured, and why it is a column and not a bar

The frozen scorer scores the failing resource and the mechanism SENTENCE
(`class_correct`). Twice (docs/failure-modes.md 2026-08-29, 2026-09-04) a
pooled number moved for reasons the rubric's vocabulary controlled, not the
agent's diagnosis. The solution arm's submission also names the FIX
(`remediation.field_path`, `current_value`, `required_value`, rendered into
the report by `solution/render.py`). The v3 column asks the question the
sentence rubric cannot: **did the agent name the right field, and the right
value?**

It is **additive and diagnostic**:

- The frozen metric, case set, `gold.json`, `scoring.py`, `scoring_v2.py` and
  every committed bundle stay byte-identical. v1's `root_cause_correct` /
  `class_correct` are read from `rows.jsonl`, never recomputed.
- It is reported beside the frozen number, never pooled with it, and sets no
  acceptance threshold. The decision doc's primary metric is unchanged.
- Arms whose contract does not carry the fields (baseline, rules) report
  **n/a**, never 0. Making the baseline emit the fields is a separate,
  disclosed contract decision and is NOT part of this slice.

## Instrument (frozen at this commit)

- Gold: `evals/gold-v3/<case_id>.json`, 15 files, schema and authoring rule
  in `evals/gold-v3/README.md`. 10 cases pin a value; 5 are open (sizes,
  replica counts, image references, URLs — gold's example is one choice among
  many), so `fix_value_correct` and `both_correct` are over the pinned rows
  only.
- Matching: normalized exact match (README "Matching"). No fixture lookup;
  name-form aliases are authored into the gold where the fixture makes them
  unambiguous.
- Accepted submission: the LAST `submit_answer` call in a row's
  `transcript.jsonl` (`solution/agent.py` breaks on the first accepted
  submit), none when `metrics.salvaged` is true or `error` is set — that row
  scores `no_submission`.
- Disclosure: before the gold was authored, exactly one submission had been
  looked at while learning the transcript format (frozen bundle, run1,
  `t1-crashloop-missing-env`: `field_path`
  `spec.template.spec.containers[name=worker].env`, `required_value` a
  free-text env block). It told me the name form exists and that
  "add an env var" values are prose; both were already in the plan. No other
  submission was read before this section was committed.

## Metric

Per tier and overall: `fix_path_correct` k/n over all rows;
`fix_value_correct` and `both_correct` k/m over rows whose gold pins a value;
counts of `no_submission` and value-open rows; per-row misses decomposed as
`path`, `value`, `path+value` or `no_submission`, with the raw submitted
strings.

| tier | rows | root_cause_correct (v1) | fix_path_correct | fix_value_correct | both_correct | no accepted submission | value open in gold |
|---|---|---|---|---|---|---|---|

| T3 | 6 | 6/6 | 3/6 | 6/6 | 3/6 | 0 | 0 |
| all | 36 | 36/36 | **16/36** | **21/21** | 12/21 | 0 | 15 |

**Prediction vs. measurement.** Path: predicted ≥ 30/36, measured 16/36 —
the prediction was wrong. Value: predicted ≥ 15/21, measured 21/21. Both:
predicted ≥ 14/21, measured 12/21 (dragged down by path). T3: predicted
path ≥ 5/6 and value ≥ 4/6, measured 3/6 and 6/6.

**Decomposition of the 20 misses: 20 path, 0 value, 0 path+value, 0
no_submission.** Every one of the 20 names the right field; every one
spells list elements as a **bare name in brackets** —
`containers[storefront].image`, `initContainers[wait-for-db].env[DB_HOST].value`,
`containers[api].readinessProbe.httpGet.port` — and one spells a map key
that way (`spec.hard[pods]`). The pre-registered normalizer strips quotes
and leaves `[x]` as written; the gold lists the `[i]` and `[name=x]` forms.
The test `test_every_frozen_bundle_miss_is_a_path_miss_in_the_bare_bracket_name_spelling`
pins this: all 20 misses match that one regex. Per case (path hits / 3):
pvc 3, rbac 3, selector-drift 3, quiet-selector 3, quota 2, crashloop 1,
cpu 1, imagepull 0, oom 0, init 0, readiness 0, overlapping 0.

So the gap is in the instrument's spelling coverage, not in what the agent
named — the same shape as the two vocabulary artifacts in
docs/failure-modes.md, now measured on a different column. The cases I
predicted would miss (crashloop, the selector cases, quota) mostly did not:
both selector cases scored 6/6, and crashloop's and quota's misses are the
same bare-name spelling.

**Post-hoc sensitivity — not the instrument.** Read by hand from the 20 raw
strings in `scoring_v3.json`: if `[x]` with a non-numeric `x` were read as
`[name=x]` on a list and `.x` on a map, all 20 would match aliases that are
already in the gold, giving path 36/36 and both 21/21. That rule change is a
candidate for a later, disclosed slice; by the rule pre-registered above it
is NOT applied here, and the committed number is 16/36.

Side observations, not scored: for the five open-value cases the
`required_value` strings are prose with examples ("an image reference that
actually resolves … e.g. busybox:1.36", "256Mi (headroom above …)") —
consistent with leaving those values open. `t1-unschedulable-cpu-requests`
runs 1 and 3 proposed `512m` (a literal re-reading of the `"512"` request);
schedulable, so not wrong by the scenario, but a reader may want more than
"a value a node can satisfy" from a fix.

### What this column says, and what it cannot

- Where the scenario pins a value and the agent submitted a fix, it named
  the right value in **27/27** rows (frozen 21/21, crossns + decoys 6/6).
- The field is the right one in every scored row by reading; the
  pre-registered spelling rule recognized it in 16/36 frozen rows and 6/7
  later rows. The miss is a rule, and the rule is now measured.
- Diagnostic column only. The frozen primary metric is unchanged. The
  column exists for one arm, so it compares nothing across arms — it says
  what the solution's fix fields contain, which the sentence rubric could
  not see.
- A `root_cause_correct` row can carry a fix the column refuses (16/36 vs
  36/36 here) for a reason that is entirely spelling; the per-row raw
  strings are in the JSON so no one has to take the pooled number's word.
