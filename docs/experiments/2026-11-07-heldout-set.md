# Experiment — a held-out case set: does the saturated score transfer? (STATUS 3.2)

## What is being tested

The frozen 12-case set is saturated (solution 36/36, CHANGELOG [8]) and every
case since has been built in the same shop/payments/orders world, with the
same page wording, by the same hands. Two things are therefore unknown:

1. **Transfer.** Whether an arm's score on an atom it has solved before
   depends on the *surface form* it solved it in — the namespace, workload,
   Service and ConfigMap names, the domain, the alert-source phrasing. The
   offline half of this question is answered (CHANGELOG [22]: the *validator*
   accepts all 36 frozen rows under a consistent rename). The live half — do
   the *agents* still find the cause — needs cases nobody tuned on.
2. **The ceiling, in two more places.** The webhook case
   (`docs/experiments/2026-09-04-webhook-outage.md`) made the cause
   structurally absent from what an arm can read and measured what each arm
   does there. That is one object kind. This set puts the cause outside the
   served universe twice more, on different kinds: a namespaced **custom
   resource** (a CRD-defined kind no tool knows) and a **core cluster-scoped
   kind no tool serves** (a Namespace's own labels).

**Claim under test, stated so it can fail:** on the three in-universe cases
(1, 3, 5 below) the solution arm scores as it does on the frozen analogs of
the same atoms (3/3 each, `confirmed`, confirmed-wrong 0); on the two
outside-universe cases (2, 4) it names the object or says it cannot, with
**confirmed-wrong 0**. A miss on an in-universe case that the frozen set
solves 3/3 is a name-dependence finding, not noise, and is read per row
before anything is pooled.

**Not tuned against.** The set is scored once per arm after it is committed.
Nothing under `solution/`, `baseline/` or `ablation/` changes to make a case
easier or harder; the one permitted touch — tolerating the new capture schema
if a tool crashes on it — is disclosed below if it happens (it did not need
to: see "Capture method").

### The new fault class — `pod-security-violation`

Pod Security admission refusing a pod for its namespace's enforce level is
not in the frozen roster and matches no frozen signature ("forbidden" is in
the rbac class's second group, but no rbac noun appears). Added to
`evals/scoring_v2.py` the way `webhook-admission-block` was: group 1 is the
stem `pod ?-?security` (plus `pss`, `security standards`), group 2 is
failure words only (`violat`, `forbidden`, `reject`, `den(y|ied)`, `refus`,
`block`, `not allowed`, `enforc`); no alternative appears in both groups; the
rollout and scheduling symptom buckets are dominated by it (a refused pod
create leaves the ReplicaSet stuck, as with the webhook class); no frozen
phrasing contains the stem, so the parity test is unaffected. Signature
tests in `tests/test_scoring_v2.py`. The v2 enum's superset test is updated
to name both additions — a disclosed instrument change, stated in the commit.

Two kind aliases are added to the v2 table for the custom kind of case 2
(`routeprofiles`, and the group-qualified spellings `routeprofile(s).fleet.
northbound.io`, all → `routeprofile`), so the identity being scored is the
object and not the plural an arm happens to write. `ns`/`namespaces` →
`namespace` already exist in the frozen table.

### Capture method

- Authoring cluster rebuilt by `evals/cluster.sh` (single-node kind, node
  image pinned by digest to v1.37.0, `busybox:1.36` imported into the node;
  the frozen set's environment). Rule 3 throughout: only the node-cached
  image, `cpu: "512"` for the unschedulable atom, no NetworkPolicy, no HPA.
- Every case follows the contract's capture protocol through `inject.sh
  --root evals/scenarios-heldout`, with the rule-6 rehearsal first: inject
  with `--no-capture`, confirm the manifest, apply `gold.json`'s remediation
  live, confirm recovery, record in `notes.md`, wipe and re-inject cleanly,
  capture, `scripts/checkpoints.sh`, commit. Tier order.
- **Capture schema 3.** Case 2 needs the pipeline to carry a CRD and its
  custom resources, so that the fixture holds the object and the ceiling
  being measured is the arms', not the benchmark's (the same reason schema 2
  added the webhook kinds). `evals/capture.sh` now records
  `cluster/customresourcedefinitions.json` (plus a describe per CRD under
  `cluster/describe/`) and, for every namespaced CRD, the custom resources
  of each namespace under `ns/<ns>/crs/<plural>.<group>.json` with their
  describes; `scenario.yaml` says `schema: 3`; `scripts/checkpoints.sh`
  requires the CRD roster on a schema-3 fixture (gate self-test in
  `tests/test_gates.sh`). The `crs/` subdirectory keeps the per-namespace
  kind files exactly the set `solution/fixture.py` expects, so no reader
  changes: a schema-3 snapshot reads through every existing tool unchanged,
  and the custom kind reads as "unknown or uncaptured" — not served, no new
  reach. `evals/inject.sh` treats a CustomResourceDefinition like a webhook
  configuration: allowed only in an additive root, only when every such
  document carries the scenario label, deleted by that label on every reset
  before the namespace wipe (a CRD outlives its namespaces), refused when an
  unlabelled one is present.
- Case 4 needs nothing new in the pipeline: `cluster/namespaces.json` has
  carried namespace labels since schema 1, and the namespace wipe is the
  reset.

### Reading rule

Results are read from `rows.jsonl` sub-scores — `resource_correct`,
`class_correct`, `matched_classes`, verdict — per row, before any pooled
number is quoted (CLAUDE.md invariant; docs/failure-modes.md 2026-08-29,
2026-09-04). Specifically:

- An in-universe miss (cases 1, 3, 5) is decomposed first: a wrong resource
  with a correct class on an atom the frozen set solves 3/3 is the
  name-dependence finding this set exists to detect; a correct resource with
  a wrong class is a vocabulary finding about the rubric, not the arm.
- On case 4, a `confirmed` row naming `deployment/gate-checkin` is read
  against its report: if the report cites the namespace's label set and
  rules it out, that is a calibration failure (confirmed-wrong, counted); if
  the report never reached the namespace because nothing served it, that is a
  reach failure first and a calibration failure second — still counted as
  confirmed-wrong, but attributed to the tool layer in the next decision.
- On cases 2 and 4, a `resource_correct` row is traced to where the name
  first appeared in the transcript (tool result, page, or a rejection
  message), as in the webhook experiment; a name learned from a validator
  message is a leak, not capability.

### Decision rule, fixed now

- In-universe cases at 9/9 with confirmed-wrong 0 and cases 2/4 at
  confirmed-wrong 0: the saturated score transfers by capability, not by
  surface form, and the ceiling is the tool layer's. The next slice serves
  namespaces (labels, annotations) through `get_object`/`describe` and opens
  CRD discovery (roadmap 2.7), then re-scores cases 2 and 4 with the
  prediction 3/3 `confirmed` each.
- Any in-universe miss: the row is examined and logged before any change to
  any arm; a name-dependence finding escalates STATUS 3.3's offline test to a
  live one (isomorphic variants of the frozen set, scored).
- Confirmed-wrong above 0 on case 2 or 4: that row is examined per the
  reading rule before anything else is concluded or built.

No bar block is added to `evals/reported.json` on this set's evidence: a
held-out set's purpose is to be read, not asserted against.

## Amendment before any scored run (2026-11-08) — case 2's ceiling is lower than designed

Found while wiring the root, before any arm ran: the validator's adversarial
sweep (`tests/test_solution_validate_adversarial.py`) over the new fixture
shows that `solution/validate.py` **V4 EXISTS** resolves the submitted
failing resource through `solution/fixture.load_kind`, which raises
`unknown or uncaptured kind 'routeprofile'` for a kind the readers do not
know; V4 reports that as `failing_resource does not resolve` and the
submission is refused **at every verdict** — `probable` and `inconclusive`
included. The solution arm therefore cannot submit the gold object on case 2
at all; it can only name a served object or exit through the salvage path.
The behaviour is pinned in the suite (`test_the_scaffold_is_satisfiable`,
the unknown-kind branch) so it stays explicit until it is changed on purpose.

**Revised prediction, solution, case 2:** `resource_correct` **0/3 by
construction**; `class_correct` 0–3 (a salvaged row's sentence classifies to
nothing); verdicts `inconclusive` (salvage) or `probable` on a served object;
the claim stays **confirmed-wrong 0**; turns, submit rejections and cost
elevated, as on the webhook case before its kinds were served. The baseline
and rules predictions are unchanged — neither passes through the validator.

**Decision rule, one item added ahead of CRD discovery:** V4 must distinguish
"no read tool serves this kind" (say so; do not refuse the name) from "the
kind is served and the object is absent" (refuse), the same not-served
discipline CHANGELOG [16] gave V1, V6 and V7 — otherwise opening the universe
(roadmap 2.7) cannot move this row, because the gate refuses the answer
before any tool is consulted. No arm code changes in this slice.

## Amendment before the rules run (2026-11-08) — case 5's decoy and the status string

Found during case 5's injections, before any arm ran: on this kubelet
(v1.37.0) a container whose process exits within seconds is reported as
`terminated/Error` through its back-off and may never show
`waiting: CrashLoopBackOff` (two injections, five minutes each, never showed
it; the optimizer in case 2, which runs ~3s before exiting, showed it every
time). The decoy's loudness is therefore not the status string — it is the
climbing restart count, exit code 1, the `BackOff` Warning event and its own
log line — and `t3-driver-login-failures/wait.sh` now gates on those. The
capture records whichever string the kubelet showed at that instant.

**Consequence for the rules prediction on case 5, stated before the run:**
`ablation/rules.py`'s crashloop analyzer keys on the `CrashLoopBackOff`
waiting reason. If the capture caught the decoy as `terminated/Error`, that
analyzer is silent, no analyzer fires (the rbac analyzer finds no binding
naming the real account either way), and the arm answers `inconclusive` with
`unknown/unknown` — still wrong, but **not** a confirmed-wrong row. The
pre-registered rules row for case 5 (confident wrong name, confirmed-wrong 3
pooled) therefore has two admissible readings, decided by the fixture's
`ns/driver-portal/pods.json`, not by the arm: `CrashLoopBackOff` → the
original prediction; `Error` → `inconclusive`, pooled confirmed-wrong **2**.
The LLM-arm predictions are unchanged: both read restart counts, exit codes
and events, not the one status string. Logged for the rules arm as a
signature that depends on a kubelet's status vocabulary rather than on the
restart evidence — a finding about the control arm, recorded, not fixed here
(the ablation is frozen with its pre-registration).

## Amendment after review (2026-11-08) — three instrument changes, before any LLM-arm run

A code review of the slice (PR #9) found three places where the v2 scorer's
own vocabulary, not an arm's behaviour, would decide a row on this set. All
three are changed in `evals/scoring_v2.py` before any LLM arm reads the set,
and the rules-arm bundle `evals/results/20261108T050338Z-rules/` was re-scored
offline through the changed scorer — the committed `run1/<case>/answer.json`
files against the committed gold, no arm re-run: **0 of 5 rows moved**
(`resource_correct` 2/5, `class_correct` 3/5, `matched_classes` identical on
every row), so the result table above stands as recorded. Each change ships
its regression test in `tests/test_scoring_v2.py`.

1. **Cluster-scoped identity ignores the namespace field.** The convention
   above ("cluster-scoped gold writes `"namespace": ""`") accepted only a
   fixed set of "no namespace" spellings from an answer. An arm that names
   the Namespace `yard-ops` on case 4 is told the paged namespace is
   `yard-ops` and has every reason to write it in the field, and that answer
   scored resource-wrong — a trap set by the rubric, not a wrong object. Now,
   for a kind the scorer knows as cluster-scoped, kind + name decide and the
   field is ignored; a namespaced kind keeps its namespace as identity.
2. **`pod-security-violation` signature tightened.** Group 1 had
   `security standards?` and group 2 had `enforc`, neither specific to the
   Pod Security plugin: "the validating webhook enforces the company's
   security standards and rejects every pod create" co-matched this class and
   scored class-wrong for the webhook case's own phrasing. Group 1 is now the
   plugin's own stems only (`pod[ -]?security` — covering "PodSecurity" in the
   API server's message, the `pod-security.kubernetes.io` label key, "Pod
   Security admission/Standards" — and `pss`); `enforc` is dropped from
   group 2. The gold self-classifies unchanged; every phrasing test passes.
3. **A spelling rule for custom kinds replaces the `routeprofile` aliases.**
   The three hard-coded aliases for case 2's kind were a per-case patch. For
   a kind the alias table does not know, the scorer now collapses `kubectl`'s
   spellings by rule — lowercase, drop the `.group` qualifier (everything
   from the first dot), drop a trailing plural `s` — so `RouteProfile`,
   `routeprofiles`, `routeprofiles.fleet.northbound.io` and
   `RouteProfile.v1.fleet.northbound.io` are one identity; every alias and
   every canonical value in the table is untouched (parametrized over the
   table). Known limit, stated: an `-es` plural (`ingressclasses`) is not
   collapsed and takes an alias when a case needs one.

Disclosed, not changed: `capture.sh` selects the Secret scrub by the kind in
its own arguments, so a custom resource embedding credentials would be captured
under the general scrub; the `fixtures free of k8s credential material` gate in
